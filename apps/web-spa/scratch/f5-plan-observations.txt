════════════════════════════════════════════════════════════════

vitest 기본 include (실측)
  ["**/*.{test,spec}.?(c|m)[jt]s?(x)"]
  → .spec.ts 가 포함된다. 우리 vitest.config.ts 에 include override 가 없다.
    (F-1 canon 의 「vitest 기본값이 scratch/ 까지 집는다」와 같은 뿌리)

e2e/probe.spec.ts 를 두고 npm test:

    when one of the dependencies in your package.json depends on @playwright/test.

  Test Files  1 failed | 152 passed (153)
       Tests  1061 passed (1061)

⚠️⚠️ 오류가 대는 원인이 우리 것이 아니다.
   "두 개의 다른 버전" 이라는데 설치본은 1.62.1 하나뿐이다.
   진짜 원인은 Vitest 가 Playwright 파일을 실행한 것.
   도구가 자기가 아는 흔한 원인을 먼저 대고, 그것이 우리 상황과 무관한 자리다.

6. strict mode 위반이 우리 앱에서 실제로 난다
════════════════════════════════════════════════════════════════

page.getByText('jaehoon', { exact: true }) →

  Error: strict mode violation: resolved to 3 elements:
    1) <span data-slot="sign-in" class="text-sm text-faint">jaehoon</span>
    2) <span class="text-sm font-semibold @lg:text-base">jaehoon</span>   (게시물 작성자)
    3) <strong>jaehoon</strong>                                          (댓글 작성자)

⇒ 로그인한 사람 · 게시물 작성자 · 댓글 작성자가 같은 글자다.
   F-3 의 「역할과 이름으로 찾는다」를 그대로 가져오면 걸리는 자리이고,
   답은 범위를 좁히는 것 — locator('[data-slot="sign-in"]').toHaveText('jaehoon')

⚠️ 이건 연출이 아니라 실제로 밟은 오류다. 지어낸 반례가 아니다.

7. ★★★ 척추 — 같은 판이 양쪽에서 통과하는데 한쪽만 실제로 그 일을 했다
════════════════════════════════════════════════════════════════

같은 spec 을 붙일 대상만 바꿔 두 번 실행.

                        MSW 목록            진짜 연습용 서버
                        (VITE_MOCK_API=1)   (:8090 켬)
  ─────────────────────────────────────────────────────────────
  카드                  10                  10
  로그인                OK                  OK
  좋아요 aria-pressed   false → false       false → true
  안 잡힌 요청          3종                 0
  판정                  ✓ 통과              ✓ 통과

MSW 쪽에서 안 잡힌 요청 (콘솔 경고로만 남는다)
  • POST http://localhost:8090/api/posts/1/like      ← 좋아요
  • ws://localhost:8090/ws                            ← C-9 STOMP 통로
  • POST http://localhost:9000/api/7/envelope/...     ← H-1 Sentry 봉투
  + 사진 20건 (picsum.photos — 진짜 인터넷으로 나간다)

⇒ 좋아요가 **조용히 되돌아간다**. 요청이 :8090 으로 새는데 서버가 꺼져 있어
   실패하고, C-7 의 낙관적 업데이트 롤백이 false 로 돌려놓는다.
   화면은 안 죽고 오류도 안 뜬다. 콘솔 경고 한 줄뿐이다.

⇒ 그리고 **판은 통과한다**. 클릭이 성공했고 앱이 안 죽었으니까.

핵심 서술: F-4 의 약속(목록이 따라온다)은 참이다. 바로 그래서 함정이 된다 —
  목록이 따라오니 앱이 살아 있어 보이고(카드 10장·로그인 OK), 그래서
  「덮여 있다」고 믿고 한 줄기를 짠다. 그런데 그 목록은 **읽기용으로 쓰였고**
  한 줄기는 **쓰기를 한다**. 쓰기는 조용히 죽는다.

사용자 결정: 둘 다 재고 대비시킨다. 이 표가 회차의 척추.

⚠️ 스텁 로그로는 판정 못 했다 — API_STUB_LOG=1 을 안 켜서 grep 이 0건이다.
   0건을 「안 갔다」로 읽으면 틀린다 (G-6 「계측이 실패하는 방법은 하나가 아니다」).
   판정 근거는 aria-pressed 전이 하나다.
