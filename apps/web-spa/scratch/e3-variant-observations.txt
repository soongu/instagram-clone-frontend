E-3 변형(상태·반응형) 관찰 (Tailwind v4.3.3 · Vite 8.1.5 · Chrome)
====================================================================

단위 테스트로 잡을 수 없는 사실을 기록한다.
빌드 산출 CSS 계측 + 브라우저 computed style / canvas 픽셀 판독 / 실제 마우스 hover.

재현 (리포지토리 루트에서):
  npm run build --workspace apps/web-spa
  LATEST=$(ls -t apps/web-spa/dist/assets/*.css | head -1)
  wc -c < $LATEST

색은 문자열이 아니라 픽셀로 잰다(E-2 와 같은 이유). 흰 배경을 먼저 칠하고
그 위에 색을 칠한 뒤 getImageData 로 읽은 값이 학생이 실제로 보는 색이다.
알파가 있는 색은 반드시 이렇게 재야 한다 — 배경 없이 칠하면 합성이 안 일어난다.


1. 변형이 만드는 CSS 규칙의 모양 (실측)
-----------------------------------------

  hover:      @media (hover:hover){ .hover\:text-ink:hover{...} }   <- 미디어로 감싼다
  disabled:   .disabled\:cursor-default:disabled{...}               <- 안 감싼다
  focus-visible:  .focus-visible\:outline-2:focus-visible{...}      <- 안 감싼다
  sm:         @media (width>=40rem){ .sm\:p-2{...} }                <- min-width 아니라 range 문법
  dark:       @media (prefers-color-scheme:dark){ ... }             <- 설정 0줄 (E-4)

  ⚠️ hover: 만 미디어로 감싸진다. 나머지 상태 변형은 순수 의사클래스다.


2. ⚠️⚠️ 출력 순서는 className 에 쓴 순서와 무관하다
-----------------------------------------------------

  probe 에 일부러 뒤집어 썼다:
    class="dark:bg-ink sm:bg-surface hover:dark:text-brand dark:hover:text-danger
           max-sm:hidden focus:outline-4 group-hover:text-brand peer-checked:block
           active:scale-95 sm:max-md:flex"

  산출 CSS 안의 위치(앞에서부터):

    3186  group-hover:text-brand
    3264  peer-checked:block
    3327  focus:outline-4
    3407  active:scale-95
    3559  max-sm:hidden
    3611  sm:bg-surface
    3699  sm:max-md:flex
    3767  dark:bg-ink
    3836  dark:hover:text-danger
    3952  hover:dark:text-brand

  dark:bg-ink 를 맨 앞에 썼는데 출력은 sm: 뒤다.
  => 특정도가 같으므로 "나중에 나온 것" 이 이긴다. 즉 dark: 가 sm: 를 이긴다.
     className 순서를 바꿔도 결과가 안 바뀐다.

  정렬 순서: 상태변형 -> max-* -> min-width 오름차순 -> dark:
  ⚠️ 임의 중단점(min-[900px]:)은 named 보다 **앞**에 나온다.
     900px > 40rem(640px) 인데도 sm: 보다 먼저다 => sm: 가 min-[900px]: 를 이긴다.
     (E-4 에서 중단점 토큰 다룰 때 이 함정을 쓸 수 있다)

  ⚠️ dark:hover: 와 hover:dark: 는 둘 다 동작하지만 중첩 순서가 반대로 나온다.
     dark:hover: -> @media(prefers-color-scheme:dark){ @media(hover:hover){...} }
     hover:dark: -> @media(hover:hover){ @media(prefers-color-scheme:dark){...} }
     매칭 결과는 같지만 출력 위치가 달라 cascade 에서 갈릴 수 있다.


3. Step 1 — .comment-submit:disabled 를 옮기며 잰 것
------------------------------------------------------

  옛 손 규칙:  .comment-submit:disabled { color: #b2dffc; cursor: default; }
  새 유틸리티: disabled:text-brand/30 disabled:cursor-default

  ⚠️⚠️ 픽셀이 1 어긋난다 — "같다" 고 쓰면 거짓이다.

    #b2dffc         흰 배경 위  178, 223, 252
    brand/30        흰 배경 위  179, 223, 252   <- R 만 1 크다

  이유: brand(#0095f6)를 30% 로 얹으면 R = 0.7 * 255 = 178.5 이고 Chrome 이 올림한다.
  눈으로는 구분 못 하지만 수치로는 다르다.

  ⚠️ 산출 CSS 에는 같은 선택자가 두 번 나온다 (@supports 점진 향상):

    .disabled\:text-brand\/30:disabled{color:#0095f64d}
    @supports (color:color-mix(in lab, red, red)){
      .disabled\:text-brand\/30:disabled{color:color-mix(in oklab, var(--color-brand) 30%, transparent)}
    }

    재미있는 것은 fallback 쪽 #0095f64d 의 알파가 0x4d = 77 이라
    255 - 77 = 178 로 옛 색과 **정확히** 같다는 점이다.
    color-mix 를 지원하는 브라우저(Chrome)만 179 가 된다.

  ⚠️⚠️ 그런데 진짜 차이는 1 픽셀이 아니라 **배경 의존성** 이다:

    배경          #b2dffc (불투명)   brand/30 (알파)
    흰색 #ffffff  178,223,252        179,223,252
    어두움 #121212 178,223,252        13,57,86      <- 배경을 타고 섞인다

    손으로 적은 hex 는 흰 배경을 전제로 고른 값이라 어두운 화면에서 그대로 밝게 뜬다.
    알파로 적으면 뒤에 무엇이 오든 그것에 섞인다.
    => E-4(다크모드)로 넘어가는 코드 근거. 지금은 둘 다 맞아 보이지만 하나만 살아남는다.

  실제 앱 실측 (dev 서버, 댓글 폼):
    잠김   color oklab(0.6546 -0.0657321 -0.164342 / 0.3) · cursor default · 픽셀 179,223,252
    풀림   color oklch(0.6546 0.177 248.2)                · cursor pointer · 픽셀 0,149,246

  ⚠️ cursor 가 잠김일 때 default 로 바뀐다 = disabled:cursor-default 가 cursor-pointer 를 이긴다.
     E-2 에서는 손 규칙이 유틸리티를 이겼는데(layer 밖 > 안), 이제는 둘 다 utilities layer
     안에 있어서 **출력 순서**로 갈린다(2번). 이긴 이유가 E-2 때와 다르다.


4. Step 2 — .comment-remove:hover 를 옮기며 잰 것
---------------------------------------------------

  옛 손 규칙:  .comment-remove:hover { color: #262626; }
  새 유틸리티: hover:text-ink

  실제 마우스를 올려서 잰 값 (computer hover -> :hover 매칭 확인 후 판독):

    평소     oklch(0.647 0 none)   = 142,142,142 (muted)
    hover 중 oklch(0.269 0 none)   =  38, 38, 38 (ink)
    옛 목표  #262626               =  38, 38, 38

  => 픽셀까지 정확히 같다. Step 1 과 달리 여기는 어긋남이 없다
     (--color-ink 가 #262626 을 정확히 옮긴 값이라서).

  ⚠️ @media (hover:hover) 가 조건이 어긋나면 정말 죽는지 실행으로 확인했다:

    #probe { color: rgb(1,2,3) }
    @media (hover: hover) { #probe { color: rgb(11,22,33) } }   -> 적용됨 (11,22,33)
    @media (hover: none)  { #probe { color: rgb(99,88,77) } }   -> 안 걸림 (1,2,3 유지)

    이 데스크톱은 matchMedia('(hover: hover)').matches === true 다.
    터치 전용 기기에서는 이 값이 false 라 hover: 유틸리티가 통째로 안 걸린다.
    (기기를 직접 바꿔 재지는 못했다 — 위 실행은 "조건이 어긋난 미디어 규칙은
     기본값을 그대로 둔다" 는 메커니즘까지만 확인한 것이다.)

6. Preflight 는 포커스 링을 없애지 않는다 (E-2 관찰 10번 정정)
----------------------------------------------------------------

  E-2 관찰 10번에 input 이 "outline none" 이라고 적었는데, 그건 포커스가 안 된
  요소를 잰 값이었다. 빌드 산출 CSS 의 @layer base 를 훑어보면 Preflight 는

     기본 링은 있고, 문제는 그 링이 우리 색·모양과 맞는가다.


7. Step 3 — focus-visible: 실측 (전부 실제 마우스/키보드로 조작해서 잼)
-------------------------------------------------------------------------

  같은 요소(게시물 메뉴 ⋯ 버튼)에 규칙만 바꿔가며 A/B/C 를 만들었다.

    규칙              조작        :focus  :focus-visible  링
    :focus            마우스 클릭  true    false           떴다 (rgb(200,0,0))
    :focus-visible    마우스 클릭  true    false           안 떴다
    :focus-visible    Tab 키       true    true            떴다 (rgb(0,200,0))

  => focus: 로 스타일하면 마우스로 눌러도 링이 뜬다. 이게 옛날 사람들이
     outline:none 을 쓰게 만든 원인이고, 그 순간 키보드 사용자도 링을 잃는다.
     focus-visible: 은 브라우저가 조작 방식을 보고 갈라준다.

  브라우저 기본 링(우리가 아무것도 안 했을 때, Tab 으로 밟았을 때):
    outline: rgb(0, 95, 204) auto 0.8px
    => 우리 brand(0,149,246)와 다른 파랑이다. Chrome 자기 색.

  ⚠️⚠️ 텍스트 입력칸은 마우스로 눌러도 :focus-visible 이 true 다.
     댓글 입력칸을 마우스로 클릭 -> :focus true · :focus-visible **true** · 링 뜸.
     버튼은 마우스 클릭에 false 인데 입력칸은 true 다.
     => "focus-visible: 은 키보드일 때만" 이라고 쓰면 거짓이다.
        명세는 "글자를 입력받아야 하는 요소" 도 포함한다.
        입력칸은 커서를 어디에 뒀는지 보여야 하니 당연한 동작이다.

  ⚠️ 프로그램 호출 el.focus() 로는 :focus-visible 이 안 켜진다(false).
     검증할 때 el.focus() 를 쓰면 "링이 안 뜬다" 는 잘못된 결론이 난다.
     반드시 진짜 Tab 키로 밟아야 한다.

  ⚠️ macOS 기본 설정에서는 버튼을 클릭해도 포커스가 안 가는 경우가 있다
     (Full Keyboard Access 설정). 이번 Chrome 에서는 클릭 시 :focus 가 붙었다.

  적용한 유틸리티 (조작 가능한 요소 8곳 전부 같은 문자열):
    focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-brand

    LikeButton · PostBody(더 보기) · PostHeader(⋯) · CommentInput
    CommentForm(게시) · CommentList(×) · TextField(입력칸) · SignUpForm(가입하기)

    실측: outline solid 2px · offset 2px · color 0,149,246 (brand 와 픽셀 일치)

  ⚠️⚠️ 가입하기 버튼은 링 색과 배경색이 같다(둘 다 brand 0,149,246). 초판에 "그래서
     대비가 약하다" 고 적었는데 **틀렸다**(1차 검수 최대 지적). outline 은 border box
     바깥에 그려지고 offset 2px 이 2px 더 밀어내므로 **링이 버튼 파랑에 닿는 지점이 없다.**
     스캔라인: 흰 → 파랑 링 2px → 흰 틈 2px → 버튼 파랑.
     즉 링 양옆이 모두 흰색이라 실제 대비는 3.17 이고 3:1 기준을 **통과한다.**
     1.00 은 offset 0 일 때의 값이다.
     => 결함은 "미달" 이 아니라 "틈 하나가 빠지면 곧바로 미달". offset 을 0으로 두면
        링과 버튼이 경계 없이 한 덩어리가 된다(실측). 과제로 남긴다.

  ⚠️ 우리가 안 건드린 요소(ProfileImagePicker 등 E-2 과제 범위 데모)는
     브라우저 기본 링을 그대로 갖는다. 아무것도 빼앗지 않았기 때문이다.

8. Step 4 — .container 가 규칙 6개인 이유 (E-1 과제 [탐구] 회수)
------------------------------------------------------------------

  빌드 산출 CSS 에서 .container 를 전부 뽑으면:

    .container{width:100%}
    @media (width>=40rem){.container{max-width:40rem}}
    @media (width>=48rem){.container{max-width:48rem}}
    @media (width>=64rem){.container{max-width:64rem}}
    @media (width>=80rem){.container{max-width:80rem}}
    @media (width>=96rem){.container{max-width:96rem}}

  기본 1개 + 중단점 5개 = 6개. E-1 답안이 적은 "1 + 5" 가 정확히 맞다.
  기본 중단점: sm 40rem(640) · md 48rem(768) · lg 64rem(1024) · xl 80rem(1280) · 2xl 96rem(1536)

  ⚠️ v4 는 min-width 가 아니라 range 문법 `(width>=40rem)` 을 쓴다.
     의미는 같지만 학생이 DevTools 에서 볼 글자가 다르다.


9. Step 5 — 반응형 피드 그리드 실측 (iframe 으로 폭 고정)
------------------------------------------------------------

  ⚠️ 창 리사이즈 도구가 이 렌더링 컨텍스트에는 안 먹었다(innerWidth 가 안 변함).
     대신 같은 페이지를 폭 고정 iframe 에 띄워 쟀다 — 미디어 쿼리는 iframe
     뷰포트를 따르므로 결과가 같다. 재현 코드는 이 파일 아래 메모 참조.

  적용:
    App     mx-auto max-w-[470px] py-4 sm:px-4 lg:max-w-[964px]
    Feed    List 에 className="lg:grid lg:grid-cols-2 lg:gap-6"
    PostCard  ... bg-surface lg:mb-0
    SignUpForm ... p-4 lg:max-w-[470px]

  뷰포트   main폭  좌우pad  ul display  카드폭  첫줄카드  카드아래여백  가입폼폭
  ------   -----   ------   ---------   -----   -------   -----------   -------
   390      390     0px      block       390      1         24px          390
   640      470     16px     block       438      1         24px          438
   700      470     16px     block       438      1         24px          438
  1023      470     16px     block       438      1         24px          438
  1024      964     16px     grid        454      2          0px          470
  1200      964     16px     grid        454      2          0px          470

  경계가 640·1024 에서 정확히 갈린다(그 값 포함). >= 이므로 640 은 이미 sm.

  숫자 확인:
    438 = 470 - 16*2                       (sm 이후 카드 폭)
    454 = (964 - 16*2 - 24) / 2            (lg 2열 · gap 24)
    390 폰에서 카드가 화면을 꽉 채운다      (base 에 좌우 padding 이 없어서)

  ⚠️ 카드 아래 여백이 24px -> 0px 로 바뀐다. 세로로 쌓을 때는 mb-6 이 간격을
     만들지만 그리드에서는 gap 이 그 일을 한다. 둘 다 두면 아래쪽만 벌어진다.
     그래서 lg:mb-0 으로 넘긴다 — 간격의 책임이 옮겨가는 자리.

  ⚠️⚠️ main 을 lg 에서 964px 로 넓혔더니 **회원가입 폼이 같이 늘어났다**(964px).
     피드만 넓히려던 건데 형제 요소가 딸려 온 것이다.
     SignUpForm 에 lg:max-w-[470px] 을 붙여 잡았다.
     "컨테이너를 넓히면 그 안의 모든 것이 넓어진다" 는 실제 사고 사례.

  자바스크립트가 한 줄도 없다. B-4 과제의 useWindowWidth 훅으로 열 수를 계산할 수도

10. 재현 — 폭을 바꿔가며 재는 iframe 방법
--------------------------------------------

  dev 서버를 띄운 뒤 브라우저 콘솔에서:

    async function atWidth(w) {
      const f = document.createElement('iframe');
      f.style.cssText = `width:${w}px;height:900px;position:fixed;left:-99999px`;
      document.body.appendChild(f); f.src = location.href;
      await new Promise(r => f.onload = r);
      await new Promise(r => setTimeout(r, 700));
      const win = f.contentWindow, d = f.contentDocument;
      const ul = d.querySelector('ul[aria-label="피드 목록"]');
      const out = { 뷰포트: win.innerWidth, display: win.getComputedStyle(ul).display };
      f.remove(); return out;
    }
    await atWidth(390); await atWidth(1200);

  ⚠️ onload 뒤에 곧장 재면 React 가 아직 안 그렸다. 700ms 정도 기다려야 한다.


11. ⚠️⚠️ 상태 변형은 순서가 아니라 특정도로 이긴다 (교안 초판 오류 정정)
--------------------------------------------------------------------------

  초판 Step 1 에 "두 규칙은 무게가 같아서 나중에 나온 것이 이긴다" 고 적었는데 틀렸다.
  선택자를 보면 무게가 다르다.

    .cursor-pointer                       클래스 1개            (0,1,0)
    .disabled\:cursor-default:disabled    클래스 1 + 의사클래스 1 (0,2,0)

  상태 변형은 의사클래스가 붙으므로 base 유틸리티보다 특정도가 높다.
  Tailwind 가 변형을 뒤에 출력하기도 해서 결과는 같지만, 이긴 **이유** 가 다르다.

  순서를 뒤집어 갈라 봤다 (조건 붙은 쪽을 먼저, base 를 나중에):

    .A:disabled { color: rgb(10,10,10) }        <- 먼저
    .A          { color: rgb(200,200,200) }     <- 나중
    => 결과 rgb(10,10,10). 먼저 썼는데도 이겼다 = 특정도가 결정.

    @media (width>=1px) { .B { color: rgb(20,20,20) } }   <- 먼저
    .B { color: rgb(210,210,210) }                        <- 나중
    => 결과 rgb(210,210,210). 나중이 이겼다 = 순서가 결정.
       미디어 쿼리는 특정도를 안 더한다.

  정리:
    상태 변형(disabled:·hover:·focus-visible:)  특정도가 더 높다 -> 순서 무관하게 이김
    반응형 변형(sm:·lg:·max-sm:)                특정도 동일     -> 출력 순서로만 갈림

  => 교안 Step 1 본문·Step 1 한 줄 정리·Step 4·마무리 핵심 하나·answers 탐구 1 을
     모두 고쳤다. 한 군데만 고치면 나머지가 서로 반박한다.

  참고: E-2 에서 손 CSS 가 유틸리티를 이긴 것은 또 다른 이유였다(cascade layer).
       layer 밖 스타일은 특정도를 따지기 전에 layer 안을 이긴다.
       즉 이 교안 3개 모듈에 "이겼다" 가 세 번 나오는데 이유가 전부 다르다.
