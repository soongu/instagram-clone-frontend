1. ⚠️⚠️ --breakpoint-* 는 :root 에 안 나온다 (커리큘럼 전제 — 실측으로 확인)
-------------------------------------------------------------------------------

  E-3 종료 상태 그대로 빌드(sm:·lg: 를 실제로 쓰고 있다):

    :root,:host 변수 29개 — breakpoint 계열 0개
    CSS 전체에서 문자열 "--breakpoint" 등장 횟수 = 0

  @theme 에 직접 두 개를 추가해도 마찬가지였다:

    --breakpoint-3xl: 120rem;
    --breakpoint-tab: 55rem;

    -> :root 변수 여전히 29개. "--breakpoint" 등장 0회.
    -> 대신 값이 미디어 조건에 그대로 박힌다:
         @media (width>=55rem){.tab\:text-brand{color:var(--color-brand)}}
         @media (width>=120rem){...}

  즉 색 토큰은 var() 로 남고, 중단점 토큰은 값이 인라인된다.
  이유: 미디어 쿼리 조건은 var() 를 못 쓴다. @media (width>=var(--x)) 는 성립하지 않는다.
  그래서 Tailwind 가 빌드 시점에 값을 계산해 박을 수밖에 없다.

  => 학생이 DevTools 에서 --color-brand 는 찾을 수 있지만 --breakpoint-sm 은 못 찾는다.
     "토큰인데 왜 안 보이지" 가 E-4 의 첫 이야기 (E-3 마무리가 지정한 자리).


2. ⚠️ 미디어 쿼리 출력 순서 — named 는 크기순, 임의는 앞으로 몰린다
---------------------------------------------------------------------

  프로브에 여러 조건을 섞어 쓰고 산출 CSS 안의 위치를 읽었다:

     9117  (hover:hover)
     9670  (width>=900px)      <- min-[900px]:  임의
     9747  (width>=40rem)      <- sm   640
     9861  (width>=55rem)      <- tab  880  (우리가 만든 named)
     9926  (width>=64rem)      <- lg  1024
    10175  (width>=120rem)     <- 3xl 1920 (우리가 만든 named)
    10246  (prefers-color-scheme:dark)   <- dark: 가 가장 뒤

  두 가지가 동시에 보인다:
    (1) 우리가 만든 named 중단점은 기본 중단점들 사이에 **크기순 제자리**로 꽂힌다.
        55rem 이 40rem 과 64rem 사이. 이름이 뭔지는 상관없고 값으로 정렬된다.
    (2) 임의 중단점 min-[900px]: 은 900px 인데도 40rem(640px)보다 **앞**이다.
        => sm: 이 min-[900px]: 을 이긴다 (E-3 canon 재확인).

  정리: 임의값은 named 무리보다 앞에 통째로 몰리고, named 끼리는 값 순서로 선다.

  ⚠️ dark: 가 모든 조건보다 뒤 = E-3 Step 4 가 비워둔 자리. 복선 회수 지점.


3. dark: 는 설정 0줄 (실측)
-----------------------------

  globals.css 에 아무 설정도 안 넣은 채 dark:bg-canvas 등을 쓰면:

    @media (prefers-color-scheme:dark){
      .dark\:border-line{border-color:var(--color-line)}
      .dark\:bg-canvas{background-color:var(--color-canvas)}
      .dark\:text-ink{color:var(--color-ink)}
      ...
    }

  ⚠️⚠️ 결정적: .dark\:bg-canvas 가 가리키는 것은 **같은** var(--color-canvas) 다.
     즉 토큰 값이 안 바뀌면 dark:bg-canvas 는 bg-canvas 와 똑같은 색을 낸다.
     "dark: 를 붙이면 알아서 어두워진다" 가 아니다. 다른 값을 어딘가에서 줘야 한다.
     이 사실이 Step 4(유틸리티마다 붙이기)와 Step 5(토큰 재정의)를 가르는 근거다.

  중첩 순서 (E-3 canon 재확인 — 둘 다 동작하지만 출력이 반대):
    dark:hover:  -> @media (prefers-color-scheme:dark){ @media (hover:hover){ ... } }
    hover:dark:  -> @media (hover:hover){ @media (prefers-color-scheme:dark){ ... } }
    dark:sm:     -> @media (prefers-color-scheme:dark){ @media (width>=40rem){ ... } }

  prefers-color-scheme 이 실제로 평가되는지 확인 (E-3 의 hover 검증과 같은 방식):
    #probe { color: rgb(1,2,3) }
    @media (prefers-color-scheme: dark)  { #probe { color: rgb(11,22,33) } }
    @media (prefers-color-scheme: light) { #probe { color: rgb(99,88,77) } }
    -> 결과 rgb(99, 88, 77). light 블록이 걸렸다.
       matchMedia('(prefers-color-scheme: dark)').matches === false
    측정 기계는 macOS 라이트 모드 (defaults read -g AppleInterfaceStyle 키 없음).


4. ⚠️⚠️ 토큰 재정의가 이기는 이유는 순서가 아니라 cascade layer 다
---------------------------------------------------------------------

  globals.css 에 이렇게 쓰면 모든 유틸리티가 따라온다:

    @media (prefers-color-scheme: dark) {
      :root { --color-canvas: oklch(0% 0 none); ... }
    }

  빌드 산출에서 각 지점이 속한 레이어를 추적했다:

    @theme 이 낸 :root,:host   위치   798   레이어 theme
    유틸리티 .bg-surface        위치  7100   레이어 utilities
    우리 다크 override :root    위치 11096   레이어 없음 (unlayered)

  왜 이기는지 순서를 뒤집어 갈라 봤다 (E-3 의 특정도 검증과 같은 방식):

    A) unlayered 를 먼저, layered 를 나중에
         #lp { --c: rgb(10,10,10) }                       <- 먼저, unlayered
         @layer theme { #lp { --c: rgb(200,200,200) } }    <- 나중, layered
         => 결과 rgb(10,10,10). **먼저 썼는데도 unlayered 가 이겼다.**

    B) 반대로 써도 결과 동일 rgb(10,10,10).
    C) 둘 다 같은 레이어 안에 두면 나중 것이 이긴다 rgb(10,10,10).

  => 결정하는 것은 **레이어**다. 순서가 아니다.
     E-2 에서 손 CSS 가 유틸리티를 이겼던 그 규칙(layer 밖 > layer 안)이
     이번에는 우리 편으로 일한다. 같은 규칙, 반대 방향.

  ⚠️ 이 과목에서 "이겼다" 의 이유 정리 (E-3 canon 에 이어붙임):
       E-2 손 CSS vs 유틸리티        cascade layer (밖 > 안)
       E-3 상태 변형 vs base         특정도 (:disabled 가 한 겹 더)
       E-3 반응형 변형끼리           출력 순서 (미디어는 특정도를 안 더함)
       E-4 다크 토큰 vs @theme       cascade layer — E-2 와 **같은** 이유
     => E-4 는 새 이유가 아니다. "네 번째 이유" 라고 쓰면 거짓.

7. ⚠️ 측정 방법 정정 — 캔버스는 알파색에서 ±1 어긋난다
--------------------------------------------------------

  E-3 채증은 알파색을 캔버스에 칠해 getImageData 로 읽었다. 이번에 같은 방법으로
  text-brand/30 을 재니 다크 카드 위에서 12,57,86 이 나왔다. E-3 기록은 13,57,86.

  분석식으로 계산하면:
    R 0.3·0   + 0.7·18 = 12.6 -> 13
    G 0.3·149 + 0.7·18 = 57.3 -> 57
    B 0.3·246 + 0.7·18 = 86.4 -> 86
  => (13, 57, 86). E-3 기록이 맞다.

  캔버스가 틀리는 이유: canvas2d 는 알파를 8비트 premultiplied 로 저장해서
  0.3 알파를 칠하는 순간 정밀도가 깎인다. 흰 배경에서도 178 이 나와
  E-3 이 구분했던 178(fallback) vs 179(color-mix) 를 재현하지 못했다
  (color-mix 지원 여부와 무관하게 세 경로가 전부 178 로 나왔다).

  => 규칙: **불투명 색은 캔버스로 재도 되지만, 알파색은 분석식으로 계산할 것.**
     E-3 의 179/13 수치는 유지한다. 이번 캔버스 값이 틀린 쪽이다.


8. ⚠️⚠️ 우리 중단점 — 그리고 E-3 의 964 가 padding 만큼 어긋나 있었다
------------------------------------------------------------------------

  E-3 은 lg(1024px)에서 2열로 갈랐다. 그 1024 는 Tailwind 가 준 숫자다.
  우리 값을 구하려고 계산하다가 E-3 의 숫자가 틀렸다는 것을 발견했다.

  E-3 은 max-w-[964px] 을 "카드 470 × 2 + gap 24 = 964" 로 잡았다.
  그런데 main 은 Preflight 때문에 border-box 라 px-4(좌우 16)가 **안쪽**을 먹는다:

    main max-w 964  ->  콘텐츠 964-32=932  ->  카드 (932-24)/2 = **454**
    main max-w 996  ->  콘텐츠 996-32=964  ->  카드 (964-24)/2 = **470**

  E-3 채증 9번이 카드 454 를 정확히 재서 적어뒀지만, 그게 의도(470)와
  어긋난다는 것은 짚지 않았다. 숫자는 맞고 해석이 빠져 있던 자리.

  그래서 E-4 는 둘을 함께 고쳤다:
    --breakpoint-2col: 62.25rem  (996px)
    2col:max-w-[996px]           (964 -> 996)
  => 한 열일 때 카드가 470 이었으니 두 열일 때도 470 이 된다.

  경계 실측 (iframe 폭 고정 — E-3 과 같은 방법):

    뷰포트  main폭  표시   열  카드폭  아래여백  가입폼
     390     390    block  1   390     24px     390
     640     470    block  1   438     24px     438
     995     470    block  1   438     24px     438
     996     996    grid   2   470      0px     470
    1024     996    grid   2   470      0px     470
    1400     996    grid   2   470      0px     470

9. 다크 값을 어디에 둘까 — 두 방식의 비용을 실제로 재봤다
------------------------------------------------------------

  (A) 유틸리티마다 dark: 짝을 붙이는 방식 — 실제로 전부 붙여보고 쟀다

    먼저 새 이름이 필요하다. dark:bg-canvas 는 **같은** var(--color-canvas) 를
    가리키므로 값이 안 바뀐다(3번). 그래서 -dark 이름을 따로 만들어야 한다:
      --color-canvas-dark / -surface-dark / -ink-dark / -muted-dark
      / -subtle-dark / -line-dark / -line-soft-dark      = 7개

    그 다음 색을 쓰는 모든 곳에 짝을 붙인다:
      bg-surface -> bg-surface dark:bg-surface-dark   식으로 **29곳 · 14개 파일**
      (index.html 2 · App 1 · ClickCounter 2 · CommentForm 1 · CommentList 2
       · KeyDemo 4 · LikeButton 2 · MiniPostCard 4 · PostBody 2 · PostCard 2
       · Section 1 · SignUpForm 2 · StaticPostCard 2 · TextField 2)

    결과: 동작은 한다. 규칙도 정상 생성된다.
      .dark\:bg-surface-dark{background-color:var(--color-surface-dark)} ...
    비용: CSS 11,171 -> 11,899 B (**+728**) · :root 29 -> 36개

  (B) 토큰을 한 곳에서 재정의하는 방식 — 최종 채택

    @media (prefers-color-scheme: dark) { :root { --color-canvas: ...; ... } }
    className 은 **한 글자도 안 고친다**.
    비용: CSS 11,171 -> 11,453 B (**+282**) · :root 29개 그대로 · 파일 1개
         (Step 6 종료 시점. Step 7 의 토스트 교체로 최종은 11,467 B)

  정리:
                    새 이름   손대는 곳    파일   CSS 증가
    유틸리티 방식      7개      29곳       14개    +728 B
    토큰 방식          0개       1곳        1개    +282 B

  ⚠️ 그렇다고 유틸리티 방식이 항상 지는 건 아니다. "이 요소만 다크에서 다르게"
     같은 국소 예외는 dark: 유틸리티가 맞다. 갈리는 기준은 **전역 규칙이냐
     한 곳의 예외냐** 지 방식의 우열이 아니다.

      뷰포트  통폭  좌우패딩  카드폭
       390    390    0px     390
       470    470    0px     470
       500    470    0px     470
       639    470    0px     470
       640    470   16px     438     <- sm:px-4 가 걸리는 순간
       995    470   16px     438

    카드가 470 인 것은 **뷰포트 470~639px 구간뿐** 이고, 교안 표는 390·640·995 만
    뽑아 390·438·438 을 보여주고 있었다. 문장이 표와 어긋난 상태.

    => 두 가지로 고쳤다.
       (1) 문장을 설계 결정 프레이밍으로: "우리가 카드 폭을 470 으로 **잡아 뒀으니**"
           (바로 위 76줄의 "카드를 470 으로 두고" 와 같은 태도)
       (2) 표에 **500 행을 추가**해 470→438 전환을 눈에 보이게 하고,
           그 아래 한 문단으로 "640 부터 sm:px-4 가 통 안쪽을 먹는다" 를 연결.
           78줄에서 글로만 설명하던 border-box 가 표에서 실제로 보인다.
       실측 재확인: 뷰포트 500 → 통 470 · 1열 · 카드 470 · 아래여백 24px (표와 일치)

  W2  "@custom-variant 한 줄을 쓰면 표시로 화면을 바꿀 수 있다" — **우리 앱엔 거짓**

    ⚠️ 이건 13번의 (3)과 **같은 뿌리인데 내가 덜 고쳤던 것**이다.
    우리 앱의 dark: 유틸리티는 **0개**다(Step 5 에서 토큰 방식을 골랐고 Step 4 의
    29곳은 되돌렸다 · `grep -rn "dark:" src index.html` = 0 · e4 테스트가
    `expect(html).not.toMatch(/dark:/)` 로 강제).
    따라서 @custom-variant 만 넣으면 .dark 를 토글해도 **아무 일도 안 일어난다.**
    움직여야 하는 것은 손으로 쓴 @media (prefers-color-scheme: dark) 블록이다.

    초판은 다음 문단이 이를 보완해 "두 문단을 묶어 읽으면 참" 이었지만,
    한 문단만 떼면 거짓이었다.
    => 세 문단으로 다시 썼다. ① 변형의 뜻이 바뀐다 ② **그런데 이 줄만으론 꿈쩍도
       안 한다 — 우리는 dark: 를 안 쓰니 옮길 곳은 그 @media 블록** ③ 바뀌는 건 조건뿐.
    => "위쪽 어딘가에" 도 "**그 요소나** 위쪽 어딘가에" 로 정밀화
       (&:where(.dark, .dark *) 는 자손뿐 아니라 자기 자신도 포함).

  ⚠️ 교훈: **한 문단만 떼어도 참인지 확인할 것.** 뒤 문단이 보완한다는 이유로
     앞 문단의 거짓을 남기면, 학생이 인용하거나 발췌할 때 그대로 틀린다.
