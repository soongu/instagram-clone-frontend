[1] 계획 단계 실행 — 착수 전제 반증
----------------------------------------------------------------------
채증(G-2) 6절은 백엔드가 resolveActor 로 신원을 가린다고 적었다.
실제로는 resolveActor 를 부르는 라우트가 좋아요 하나뿐이다.

  server.mjs:442  좋아요  → resolveActor(req.headers)      Bearer / X-Actor 둘 다
  server.mjs:359  팔로우  → req.headers['x-actor'] 직접     X-Actor 만

 같은 신원, 같은 앱, 두 버튼:
                              좋아요 /posts/1/like   팔로우 /users/minji/follow
  X-Actor: jaehoon            200                    200
  Authorization: Bearer <진짜>  200                    401   ← 갈린다
  Authorization: Bearer nope   401                    401
  (아무 헤더 없음)              401                    401

 ⇒ 화해는 프런트만 고쳐서 되는 일이 아니다. 백엔드가 같은 규칙을 갖고 있어야 한다.
   C-5 가 쓴 "프런트만으로는 못 정해요"(C5-lecture.md:702)가 과목 마지막 날 실물로 돌아온다.


[2] Step 1 — 번호표 하나에서 두 개로
----------------------------------------------------------------------
설정: session: { cookieCache: { enabled: true, maxAge: 60 } }

 켜기 전 (기본값):  쿠키 1개
   better-auth.session_token   79자(항아리 표기) = 토큰 32 + '.' + 서명 46

 켠 뒤:            쿠키 2개
   better-auth.session_token   79자   (그대로)
   better-auth.session_data   955자   (통째로 새로 생김)

 ⚠️ 서명 길이 46 vs 44 — 둘 다 참이고 조건이 다르다.
    항아리/개발자 도구에 적힌 그대로   = 46 (마지막 '=' 가 %3D 로 적힌다)
    퍼센트 인코딩을 풀면              = 44
    G-1 교안이 46 으로 적었으므로 G-3 도 같은 기준(항아리 표기)을 쓴다.

 ⚠️ 955 는 재훈으로 로그인했을 때. 민지는 947 (아이디가 두 글자 짧고 네 군데에 들어간다).
    같은 사람이 세 번 로그인해도 955 로 일정하다.

 session_data 를 base64url 로 풀면 (마침표가 0개 — 통째로 한 덩어리):
   {"session":{"session":{"expiresAt":"…","token":"…","userId":"…"},
    "user":{"name":"재훈","email":"jaehoon@example.com",…,"username":"jaehoon",…},
    "updatedAt":…,"version":"1"},"expiresAt":…,
    "signature":"3DsZk5Ll1NaFdua_tfSz…"}
   ⇒ 서명은 JSON 안에 들어 있다. 학생이 자기 이메일을 눈으로 읽을 수 있다.
   ⇒ 서명은 "고쳤는지" 를 잡을 뿐 "못 읽게" 하지는 않는다.

 1.7.1 소스 실측 (node_modules/@better-auth/core/src/types/init-options.ts:1073)
   maxAge?: number       기본 300 (5분)
   enabled?: boolean     기본 false
   strategy?: "compact" | "jwt" | "jwe"   기본 "compact"
   refreshCache?: boolean | { updateAge?: number }   기본 false
   version?: …           (G-2 채증에 없던 옵션)


[3] Step 2 — 서버가 잊어도 돌아온다 (코드 변경 없음 · 측정)
----------------------------------------------------------------------
절차: 로그인 → dev 서버 kill → 재시작(메모리 저장소 소멸 · 계정도 새 id 로 다시 심김)
      → 같은 항아리로 계속 요청

 되살아난 쿠키가 말하는 사람 : userId mDMpdglQ8DKgpLnNQQk66xuWKPLtO3s8
 새 서버의 진짜 재훈          : userId x8cDlyubXHXVYzrAhE9rFEvrQ8M5Uos7
 ⇒ 서버에 없는 사람으로 통과한다.

 ★ 2x2 로 갈라야 정확하다 (한 축만 보면 틀린 결론이 난다)

                        보내는 쿠키    get-session   /minji
  저장소 O · 기간 안     token+data    세션있음       200
  저장소 O · 기간 뒤     token 만      세션있음       200   ← 저장소로 되돌아갈 뿐, 아무 일 없음
  저장소 X · 기간 안     token+data    세션있음       200   ← 되살아났다
  저장소 X · 기간 뒤     token 만      null          200   ← 신원은 죽고 문지기는 통과

 실측 타임라인 (maxAge 60 · 저장소 비운 서버):
   T+15/30/45/55s  세션있음 · /minji 200
   T+62/70/80s     null    · /minji 200

 ⚠️ 측정 함정 두 개를 직접 밟았다.
   (1) 저장소가 살아 있는 서버에서 재면 만료돼도 계속 「세션있음」이라
       "채증이 틀렸다" 고 결론 낼 뻔했다. 갈리는 것은 저장소가 비었느냐다.
   (2) `curl -v` 출력을 통째로 grep 하면 응답의 Set-Cookie 까지 세어져
       "만료 뒤에도 보낸다" 는 거짓이 나온다. `^> Cookie:` 로 시작하는 줄만 봐야 한다.
       바로잡으면: 60초 뒤엔 정말 안 보낸다(Max-Age=60).

 Set-Cookie 원문:
   better-auth.session_token=…; Max-Age=604800; Path=/; HttpOnly; SameSite=Lax
   better-auth.session_data =…; Max-Age=60;     Path=/; HttpOnly; SameSite=Lax
   ⇒ 쿠키 자체의 만료(60초)와 봉투 안의 "expiresAt"(60초)이 둘 다 걸려 있다.

 ★ 마지막 줄이 G-2 Step 1 과 만나는 자리다 — 문지기는 session_token 의 존재만 보므로
   신원이 사라져도 계속 통과시킨다. G-2 가 "낙관적" 이라 부른 성질 그대로.


[4] 🚨 Step 2 의 결론이 「재는 방법」에 달려 있었다 (직접 밟은 사고)
----------------------------------------------------------------------
G-2 채증 4절은 이렇게 적었다:
  "같은 항아리 · 같은 서버 · 60초 지난 뒤 → get-session null · GET /minji 200 (!)
   ⇒ 신원은 사라졌는데 문지기는 여전히 통과시킨다."

이것은 `curl -b jar`(읽기 전용 항아리)로 잰 값이다. 항아리를 갱신하면(-b -c) 정반대다.

                         -b 만 (항아리 안 갱신)   -b -c (브라우저처럼)
  T+20/45s (기간 안)      세션있음 · 200          세션있음 · 200
  T+65s~   (기간 뒤)      null    · 200          null    · 307 · 항아리 0개

만료 시점의 응답 헤더를 잡아보면 이유가 나온다:
  set-cookie: better-auth.session_token=;   Max-Age=0; Path=/; HttpOnly; SameSite=Lax
  set-cookie: better-auth.session_data=;    Max-Age=0; Path=/; HttpOnly; SameSite=Lax
  set-cookie: better-auth.dont_remember=;   Max-Age=0; Path=/; HttpOnly; SameSite=Lax

 ⇒ 서버가 세 쿠키를 걷어간다. 진짜 브라우저는 그 말을 듣고, 다음 요청부터 문지기가 막는다.
 ⇒ 「신원은 죽고 문지기는 통과」는 교안에 쓰면 안 된다 — 학생 화면에서 재현되지 않는다.
 ⇒ 진짜 대가는 그것이 아니라 **유효기간 안에는 저장소가 비어도 통과한다** 쪽이다.

 캐논 적중: "게이트가 동작을 흉내 낼 때 흉내 내는 방법이 측정값을 바꾼다."


[5] Step 3 — 가릴 수 있나 · 즉시 무효화는 · 그래서 어떻게 정하나
----------------------------------------------------------------------
(가) strategy: 'jwe'   — 진짜로 가린다
  session_data  955자(compact) → 1124자(jwe) · 마침표로 나뉜 5조각
    116 / 0 / 22 / 939 / 43
  머리 조각만 풀린다: {"alg":"dir","enc":"A256CBC-HS512","kid":"Pmjxv…"}
  이메일 · 「재훈」 · 「jaehoon」 전부 안 보인다. /minji 200 · tsc 0 (그대로 동작)
  ⇒ compact 는 서명만, jwe 는 암호화. 서명은 「고쳤는지」를 잡고 「못 읽게」는 안 한다.

(나) refreshCache: true — 대가를 줄이는 게 아니라 키운다
  20초마다 두드리며 저장소를 비운 서버에서:
    T+20/40/60s  세션있음 · 200
    T+80s~       null    · 307
  문서: "refreshed BEFORE expiry ... WITHOUT querying the database"(80% 지점)
  ⇒ 저장소를 아예 안 보고 스스로 기간을 늘린다. 즉시 무효화에서 더 멀어진다.

(다) [대조군] 끈 상태 — 되살아나는 창이 아예 없다
  로그인 직후 쿠키 1개 → 저장소 비우고 **즉시** null · /minji 307 · 항아리 0개

  요약                    켬(maxAge 60)        끔(기본값)
  로그인 직후 쿠키        2개 (+955자)          1개
  저장소 비운 직후        세션있음 · 200         null · 307
  유효기간 지난 뒤        null · 307            —

 ⇒ 결정: 켜지 않는다. 우리 앱에는 나가기 버튼이 있고, 나가는 순간 끝나는 쪽이 더 중요하다.
   (사용자 승인 2026-08-20)


[6] Step 4 — 남의 집 열쇠를 붙인다 (가짜 열쇠)
----------------------------------------------------------------------
설정: socialProviders: { github: { clientId: 'demo-client-id', clientSecret: 'demo-secret' } }
      (환경 변수 GITHUB_CLIENT_ID / GITHUB_CLIENT_SECRET 가 없으면 이 값으로 떨어진다)

머리말에 「GitHub 으로 계속하기」 버튼 신설.
  · 아이디·비밀번호 폼과 목적지가 달라 <form> 을 따로 뒀다 (폼 하나에 보낼 곳은 하나).
  · 서버 액션 signInWithGitHub 하나뿐이고 'use client' 없이 동작한다.

폼을 실제로 제출하면:
  HTTP/1.1 303 See Other
  Location: https://github.com/login/oauth/authorize
    ?response_type=code
    &client_id=demo-client-id
    &state=<32자>
    &scope=read%3Auser+user%3Aemail
    &redirect_uri=http%3A%2F%2Flocalhost%3A3000%2Fapi%2Fauth%2Fcallback%2Fgithub
    &code_challenge_method=S256
    &code_challenge=<43자>

  ⇒ redirect_uri 가 G-1 이 만든 캐치올 라우트를 가리킨다 (복선 회수 지점).
  ⇒ 가짜 열쇠인데도 「어디로 보낼지」는 진짜로 만들어진다.

숨은 입력은 $ACTION_ID_… 하나뿐이고 value 속성이 없다 (D-8 canon 과 같은 모양).

 ⚠️ 측정 노트 — curl 로 서버 액션 폼을 제출할 때 인코딩을 맞춰야 한다.
    --data-urlencode → HTTP 200 (액션이 아예 안 돈다. 평범한 화면만 돌아온다)
    -F (multipart)   → HTTP 303 + Location   ← 폼이 선언한 encType 과 같다
    앞엣것만 보고 "버튼이 동작 안 한다" 로 읽으면 틀린다.


[7] Step 5 — 검사를 일부러 깨뜨린다 (코드 변경 없음 · 측정)
----------------------------------------------------------------------
시작 요청이 우리 쪽에 쿠키를 하나 심는다: better-auth.state (81~83자, 그때그때 다름)

 콜백에 들고 간 것              돌아온 오류
 state 없음                    state_not_found
 state 틀림                    state_mismatch
 state 맞음 · 항아리 없음        state_mismatch     ← 주소의 state 만으로는 못 통과한다
 state 맞음 · 항아리 있음        invalid_code       ← 검사를 통과해 code 교환까지 갔다

 같은 state 를 두 번:  1회 invalid_code / 2회 state_mismatch
 ⇒ 한 번 쓰면 사라진다.

 ⇒ state 는 「주소에 실린 값」과 「우리가 심은 쿠키」가 짝이 맞는지를 본다.
   짝이 맞아야만 다음(code 교환)으로 넘어가고, 거기서 가짜 code 가 걸린다.
 ⇒ 여기까지가 우리 몫이다. invalid_code 를 넘어가려면 GitHub 에 앱을 등록해야 한다 —
   강의는 여기서 정직하게 멈춘다.

 GitHub 이 실제로 하는 말 (그 주소로 가보면):
   HTTP/2 302 · location: https://github.com/login?client_id=demo-client-id&return_to=…
   ⇒ 우리 몫은 주소를 만드는 데까지. 그다음은 GitHub 의 화면이다.

[9] Step 7 — 서명된 것으로 바꿔본다 → 반쪽만 통한다
----------------------------------------------------------------------
신설 lib/backend-token.ts — 사람마다 백엔드 출입증을 하나씩 들고 있는다.
  · globalThis 에 매단다 (G-1 Step 6 의 저장소가 셋이 되는 사고와 같은 이유)
  · 브라우저로는 한 글자도 안 나간다 — C-5 가 localStorage 에 뒀던 그 토큰이다
액션 둘은 headers 를 { 'X-Actor': me } 에서 { Authorization: `Bearer ${token}` } 로.

앱에서 팔로우를 실제로 눌러보면:
  폼 제출 HTTP 200 · 민지 팔로워 8500 → 8500   (안 움직인다)
  스텁 로그: POST /api/auth/login → POST /api/users/minji/follow  (요청은 갔다)

같은 토큰을 스텁에 직접:
  팔로우 /users/minji/follow  → {"success":false,…,"message":"로그인이 필요합니다"}
  좋아요 /posts/2/like        → {"success":true,"data":{…,"likeCount":8499},…}

 ⇒ 같은 신원 · 같은 앱 · 같은 방식인데 한쪽만 통한다.
   server.mjs:442 좋아요는 resolveActor(토큰도 이름도 받는다)
   server.mjs:359 팔로우는 req.headers['x-actor'] 를 직접 읽는다
 ⇒ 프런트에서는 이 차이가 안 보인다. 둘 다 200 이던 것이 하나만 깨진다.

 ⚠️ 좋아요 폼은 curl 로 못 누른다 (D-8 canon 재현):
    action="javascript:throw new Error('React form unexpectedly submitted.')"
    숨은 $ACTION 입력 0개 — useOptimistic 이 붙으면 자바스크립트 전용 폼이 된다.
    그래서 좋아요 쪽 판정은 스텁에 직접 쏘는 것으로 갈음했다.

 ⚠️ 측정 함정 두 개를 또 밟았다.
   (1) 측정 스크립트가 아예 없는데 「안 움직였다」가 출력됐다 — 침묵이 실패로 읽힐 뻔했다.
       스크립트가 큰 소리로 죽게 고쳤다(FORM_NOT_FOUND / ACTION_FIELDS_NOT_FOUND).
   (2) `: > stub.log` 로 로그를 자르면 안 된다. node 가 옛 offset 에 계속 써서
       앞부분이 NUL 로 채워지고 `file` 이 "data" 라고 답한다(grep 이 조용해진다).
       자르지 말고 `wc -l` 로 기준선을 잡고 `tail -n +N` 으로 새 줄만 본다.
