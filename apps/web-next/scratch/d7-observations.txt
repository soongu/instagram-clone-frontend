0절. 계획 단계 실행 — 이번엔 커리큘럼이 아니라 분량을 반증했다

5절. Step 5 — 이름표를 얼마나 굵게 부를 것인가 (계획에서 바뀐 Step)
════════════════════════════════════════════════════════════════════════
⚠️⚠️ 계획안의 Step 5 는 "revalidateTag 는 즉시가 아니다" 였는데 **Server Action 안에서는
   그 차이가 안 보인다**. 실측: 액션 안에서 updateTag → revalidateTag(tag,'max') 로
   한 줄만 바꿔도 화면이 **요청1부터 8501**(즉시). 액션이 스스로 다시 그리면서 캐시를
   이미 채워버리기 때문이다. 차이가 드러나는 자리는 **다시 그리지 않는 Route Handler**
   뿐이라 그 측정을 6절(Step 6)로 옮기고, Step 5 는 **태그 굵기**로 다시 잡았다.
   D-6 이 이름표를 둘(`profile` + `profile:{username}`) 붙여둔 것이 여기서 값을 한다.

실험 설계: 두 화면(/minji · /jaehoon)의 캐시를 채우고, Next 를 안 거치고 두 사람의
원본을 함께 바꾼 뒤, **minji 프로필에서만** 팔로우를 누른다.

  [가는 이름표] updateTag(`profile:minji`)
    minji    원본 8501 · 화면 **8501**  ← 갱신됨
    jaehoon  원본 1241 · 화면 **1240**  ← 낡은 채로 남는다 (안 건드렸으니까)

  [굵은 이름표] updateTag('profile')
    minji    원본 8500 · 화면 **8500**  ← 갱신됨
    jaehoon  원본 1240 · 화면 **1240**  ← 안 건드렸는데 **따라 갱신됐다**(1241→1240)

  ⇒ 굵게 부르면 편하지만 남의 캐시까지 버린다. 실험 후 가는 이름표로 원복.

6절. Step 6 — Route Handler, 그리고 revalidateTag 의 진짜 얼굴
════════════════════════════════════════════════════════════════════════
`app/api/profiles/revalidate/route.ts` — POST 만 export.

라우트 표에 새 줄과 **새 범례**가 생긴다:
  ├ ƒ /api/profiles/revalidate
  ◐  (Partial Prerender)  ...
  ƒ  (Dynamic)            server-rendered on demand      ← D-5 이후 처음 돌아온 범례

★★★ revalidateTag(tag,'max') 는 stale-while-revalidate 다 (Route Handler 실측):
  ① 캐시를 채운다        화면 8500 · 원본 8500
  ② 원본만 바꾼다        화면 8500 · 원본 8501
  ③ POST /api/profiles/revalidate?username=minji → {"success":true,...}
  ④ 요청1 **8500**  ← 아직 옛 숫자!
     요청2 8501 · 요청3 8501 · 요청4 8501 · 요청5 8501
  ⇒ 버린 직후 한 번은 옛것을 더 준다. 문서 그대로:
    "Serves cached data while fetching fresh data in the background"
  ⇒ 자기가 방금 한 일을 자기가 봐야 하는 자리에선 이걸 쓰면 안 된다 → updateTag

덤으로 얻은 것:
  · username 없이 부르면 400 + 우리가 쓴 메시지 (우리가 만든 응답)
  · **GET 으로 부르면 405** — 우리가 안 만든 응답인데 Next 가 낸다(POST 만 export 해서)

[반례] 같은 Route Handler 에서 updateTag 를 부르면:
  next build **exit 0** · tsc **0** · 그런데 런타임 **500**
  ⨯ Error: updateTag can only be called from within a Server Action.
    To invalidate cache tags in Route Handlers or other contexts, use revalidateTag
    instead. See more info here: .../functions/updateTag
  → D-6 Step 5 와 같은 계열("통과했는데 틀린 것"). 에러가 해법을 그대로 말한다.
  소스 실측(next/dist/server/web/spec-extension/revalidate.js):
   · updateTag 는 workStore 가 없거나 `workStore.page.endsWith('/route')` 면 던진다(E872)
   · revalidateTag 는 2번째 인자가 없으면 console.warn 으로 deprecation 을 찍는다

7절. Step 7 — proxy.ts 로 404 를 되찾는다
════════════════════════════════════════════════════════════════════════
`apps/web-next/proxy.ts` (app 폴더 밖, 프로젝트 뿌리)

  NextResponse.rewrite(new URL('/_not-found', request.url), { status: 404 })
  ⚠️ 공식 문서 rewrite 절에는 status 예시가 **없다**. 타입에서 찾았다 —
     rewrite(destination, init?: MiddlewareResponseInit) 이고
     MiddlewareResponseInit extends globalThis.ResponseInit 라 status 가 있다.
     (node_modules/next/dist/server/web/spec-extension/response.d.ts)

라우트 표 끝에 새 줄:  `ƒ Proxy (Middleware)`
  ★ 파일 이름은 proxy.ts 인데 표에는 아직 (Middleware) 라고 적힌다.
    응답 헤더도 `x-middleware-rewrite: /_not-found` — 옛 이름이 두 군데 남아 있다.

상태 코드 실측:
  /  200 · /explore 200 · /jaehoon 200 · /minji 200 · **/zzzzz 404** · **/a/b/c 404**
  /zzzzz 본문: "없는 주소예요" 3 · "주소를 다시 확인해주세요" 3 · "피드로 돌아가기" 3

  ⇒ D-4 가 401ms 주고 샀고 → D-5 가 스위치 하나로 되팔았고 → D-6 이 못 되찾았고
    → D-7 이 화면 밖에서 되찾았다. 3회차에 걸친 아크가 닫힌다.

8절. Step 8 — 그 404 의 값
════════════════════════════════════════════════════════════════════════
첫 바이트(time_starttransfer) 5회씩 · 같은 기계 · 클린 빌드 후:

              proxy 없음(D-6 끝)        proxy 있음
  /           200 / 2.1~3.9ms           200 / 1.6~3.3ms
  /explore    200 / 1.9~5.0ms           200 / 1.4~1.5ms
  /jaehoon    200 / 2.0~5.5ms           200 / **403.8~406.1ms**
  /zzzzz      **200** / 1.6~2.2ms       **404** / 403.2~405.0ms

  ★ 404 를 되찾는 값 = 프로필 주소 전부의 첫 바이트가 약 2ms → 405ms.
    405ms 의 정체는 api-stub 의 DELAY_MS(400) — proxy 가 "이 사람 있나" 를 묻고
    답이 와야 첫 바이트가 나간다. 계산이 맞는 통제된 숫자다.
  ★ matcher 가 제외한 / 와 /explore 는 전혀 안 문다 — 무는 범위는 우리가 정한다.

⚠️ proxy 는 Server Action POST 도 문다 (문서 「Execution order」 경고의 실측):
  "Server Functions ... are handled as POST requests to the route where they are used"
  팔로우 한 번의 api-stub 요청 추적:
    GET  /api/users/minji          ← proxy 의 존재 확인 (쓰기엔 필요 없다)
    POST /api/users/minji/follow   ← 진짜 일
    GET  /api/posts?username=minji ← 다시 그리기
    GET  /api/users/minji/tags     ← 다시 그리기
    GET  /api/users/minji          ← updateTag 로 버린 것 다시 만들기
  존재 확인 요청 증가분 **3건**

[고침] matcher 는 method 를 안 가리므로 코드에서 가른다:
  if (request.method !== 'GET') return NextResponse.next();
  → 존재 확인 증가분 **3건 → 2건** · 404 는 그대로(/zzzzz 404 · /a/b/c 404)
  → /jaehoon 첫 바이트는 여전히 406ms (GET 은 계속 확인한다 — 그게 404 의 값이다)

    클릭1 원본 8501→8501(불변) · 재조회 **+1**  → 실패. 캐시를 안 건드렸다

  ⇒ 실패하면 updateTag 를 안 부르므로 화면 숫자가 안 흔들린다.

  matcher: '/((?!api|_next|favicon.ico).+)'  (explore 제거)

  ⇒ matcher 는 "안 볼 것" 을 적는 자리이고, 빠뜨리면 멀쩡한 화면이 사라진다.

  POST 는 확실히 실행되고(부작용·api-stub 로그로 확인) Set-Cookie 도 오는데,
  `/minji` 처럼 스트리밍하는 화면에서는 본문이 30초를 기다려도 0 B 다.
  그래서 **액션의 반환값(오류 메시지)은 부작용으로 갈랐다** — 성공/실패를
  "프로필 재조회 +3 vs +1" 로 판별(9절). 화면 문구 확인은 학생이 브라우저에서 한다.
  (Step 2 의 signIn 은 `/` 가 덜 스트리밍해서 본문이 잡혔다.)

⚠️ **측정 한계 2 — 숨은 탭 함정 재현(C-9·E-7·D-2 선례).**
  브라우저에서 200ms×30 폴링을 돌렸더니 CDP 45초 타임아웃으로 렌더러가 죽은 것처럼
  보였다. `visibilityState:"hidden"` 에서 setTimeout 이 조여진다. 그리고
  `document.body.innerText` 는 숨은 탭에서 빈 문자열이라 **textContent** 를 써야 한다.
  이번엔 클릭 직후 evaluate 도 얼어서, 반복 시도를 멈추고 서버 측 증거로 갈아탔다.
