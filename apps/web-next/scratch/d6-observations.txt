────────────────────────────────────────────────────────────────────────
2절. instant = false 의 정체 (문서 대조)
────────────────────────────────────────────────────────────────────────
빌드 에러는 `[block] Set export const instant = false to allow a blocking route` 라고
말하지만, 실제 의미는 **정적 껍데기 검사(static shell validation) 면제**다.

  · instant 문서(lastUpdated 2026-08-03): "Cache Components also validates that each
    page in your app produces a non-empty static shell at prerender time. To opt a route
    out of this validation, ensure the highest `instant` config in the route's tree is false."
  · 검증 레벨은 'warning' 하나뿐이고 개발 중에만 돈다.
  · 런타임 동작을 바꾸지 않는다 → D-5 에서 instant = false 를 달아둔 채로도
    x-nextjs-prerender: 1 + x-nextjs-postponed: 1 이 그대로 찍혔다.

  ⇒ D-5 교안의 서술("이 주소는 미리 그리기 검사를 건너뛰어라")은 문서와 정확히 일치.
     정정 불필요.

3절. 우리가 정한 적 없는 숫자 (Step 1)
────────────────────────────────────────────────────────────────────────
응답 헤더 (모든 라우트 공통):
  x-nextjs-stale-time: 300      ← default 프로필의 stale 5분
  x-nextjs-prerender: 1
  x-nextjs-postponed: 1

★ 주의 — 이 헤더는 **라우트 껍데기**의 stale 이지 개별 캐시 함수의 값이 아니다.
  fetchProfile 에 cacheLife({ stale: 30, ... }) 를 걸어도 헤더는 300 그대로였다.

api-stub 프로필 응답에 countedAt(집계 시각) 신설 → 화면에 "(오전 10:05:51 기준)".

  req1  10:06:52 → 오전 10:05:51
  req10 10:07:30 → 오전 10:05:51      100초간 단 한 번도 안 바뀜

4절. cacheLife — 수명이 눈에 보이는 순간 (Step 2)
────────────────────────────────────────────────────────────────────────
프리셋 (문서 lastUpdated 2026-08-18):
  profile   stale      revalidate   expire
  default   5분        15분         없음
  seconds   30초       1초          1분
  minutes   5분        1분          1시간
  hours     5분        1시간        1일
  days      5분        1일          1주
  weeks     5분        1주          30일
  max       5분        30일         1년

fetchProfile 에 cacheLife({ stale: 30, revalidate: 5, expire: 60 }) → 1초 간격 20회 polling:

  t=1s   오전 10:08:08
  t=4s   오전 10:08:14     (+6.7s)
  t=7s   오전 10:08:21     (+6.7s)
  t=10s  오전 10:08:28     (+6.7s)
  t=13s  오전 10:08:34     (+6.7s)
  t=16s  오전 10:08:41     (+6.7s)
  t=19s  오전 10:08:48     (+6.7s)

★ revalidate 를 5초로 정했는데 실제 주기는 약 6.7초. 다시 만드는 데 걸리는 시간
  (프로필 요청 ~1.7초)이 얹힌다. revalidate 는 "정확히 N초마다"가 아니라
  "N초가 지난 뒤 다음 요청부터 다시 만든다".

최종 확정: fetchProfile / findProfile 모두 cacheLife('hours').

문서가 준 임계값(프리렌더에서 빠지는 조건) — 과제로 돌림:
  · revalidate 0 또는 expire < 5분  → 프리렌더 제외(요청 때 채우는 구멍)
  · stale < 30초                    → 제외(프리페치가 클릭 전에 만료)
  · stale 30초~5분                  → 프리렌더엔 들어가되 App Shell 에선 제외
  프리셋 중 조건에 걸리는 것은 seconds 하나뿐(expire 1분).

상태 코드만 200.

★ 껍데기를 넓히는 것으로는 404 가 안 돌아온다. 문서가 못 박는다:

  loading.js 「Status Codes」(lastUpdated 2026-06-08):
    "When streaming, a 200 status code will be returned... Because the response headers
     have already been sent to the client, the status code of the response cannot be updated."
    "If you need a 404 status, for compliance or analytics, ensure the resource exists
     before the response body is streamed."
    "The response body starts streaming when a Suspense fallback renders... Place
     notFound() before those boundaries and before any await that may suspend."

  notFound() 문서(lastUpdated 2026-07-24):
    "With Cache Components, every dynamic route streams a static shell first, so run that
     check in `proxy` instead."

  ⇒ 회복 도구는 proxy = D-7 소관. D-6 은 "왜 이 화면 안에서는 안 되는가" 까지.
