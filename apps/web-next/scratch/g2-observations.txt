  ⇒ 어디로 가려고 했는지가 응답 어디에도 안 남는다. (G-1 약속 #2 확인)

[2] 세션의 실체 — 기본값은 번호표 하나
----------------------------------------------------------------------
sign-in/username → 200, 항아리에 쿠키 1개
  better-auth.session_token = sdT92qomyHLfLhEeXFnTNaPMxJtL... (32자 + 서명)
  ※ 세션 데이터 쿠키는 없다. get-session 은 매번 저장소를 조회한다.


[3] cookieCache 를 켜면 — 쿠키가 하나 더 생기고, 그 안이 다 보인다
----------------------------------------------------------------------
설정: session: { cookieCache: { enabled: true, maxAge: 60 } }

로그인 후 쿠키 2개:
  better-auth.session_token  (32자   — 번호표)
  better-auth.session_data   (955자  — 데이터 통째)

session_data 를 base64url 로 풀면 (서명만, 암호화 아님):
  {"session":{"session":{"expiresAt":"2026-08-27T07:57:05.866Z",
   "token":"RJIG9w2H0MeCFvvIgCwhnn5ooaoOkjV4",...,
   "userId":"MHzSKEgFGcKX8YDoSCLomd8BImIoY7ZJ"},
   "user":{"name":"재훈","email":"jaehoon@example.com",...
  ⇒ 학생이 자기 이메일을 눈으로 읽을 수 있다.

1.7.1 소스 기준 옵션 (node_modules/@better-auth/core/src/types/init-options.ts:1073)
  maxAge?: number          기본 5분(300)
  enabled?: boolean        기본 false
  strategy?: "compact" | "jwt" | "jwe"    기본 "compact"
  refreshCache?: boolean | { updateAge?: number }   기본 false

🚨 커리큘럼 원안의 "DB 세션 vs JWT" 는 next-auth 어휘다.
   Better Auth 에는 session.strategy 토글이 없다. session_token 은 항상 번호표이고,
   JWT 는 그 캐시 쿠키의 인코딩 형식 셋 중 하나일 뿐이다.
   → 교안은 "번호표만 들 것이냐 / 잠깐 베껴 들고 다닐 것이냐" 로 간다.


[4] 🔬 그 대가 — 서버가 세션을 잊어도 통과한다
----------------------------------------------------------------------
절차: cookieCache 켠 채 로그인 → dev 서버 kill → 재시작(메모리 저장소 소멸,
      계정도 새 id 로 다시 심김) → 같은 항아리로 요청

캐시 유효기간 안 (60초 이내):
  get-session → {"session":{"id":"reTuXMJ3Men5Ek4Uckfq3KTfWmcouP39",
                 "userId":"MHzSKEgFGcKX8YDoSCLomd8BImIoY7ZJ",...
  GET /minji  → 200
  ⇒ 서버에 그 세션도 그 계정도 없는데 신원이 살아 돌아왔다.

같은 항아리 · 같은 서버 · 60초 지난 뒤:
  curl 이 보내는 쿠키: session_token 하나뿐 (session_data 는 만료돼 안 감)
  get-session → null
  GET /minji  → 200 (!)
  ⇒ 신원은 사라졌는데 문지기는 여전히 통과시킨다.

★ [1]·[4] 가 한 자리에서 만난다: 문지기 통과 + 화면 로그아웃.
  공식 문서가 getSessionCookie 를 "optimistically redirect" 용이라 부르고
  "각 페이지·액션에서 반드시 검증하라" 고 못박은 문장의 실물.


[5] 소셜 — 진짜 OAuth 앱 등록 없이도 '주소' 는 실물이다
----------------------------------------------------------------------
설정: socialProviders: { github: { clientId: 'demo-client-id', clientSecret: 'demo-secret' } }

POST /api/auth/sign-in/social {"provider":"github","callbackURL":"/"}
 → {"url":"https://github.com/login/oauth/authorize?
      response_type=code
      &client_id=demo-client-id
      &state=mucUwLL3Gv-8HUwNArowx7WFEeta7fyT
      &scope=read%3Auser+user%3Aemail
      &redirect_uri=http%3A%2F%2Flocalhost%3A3000%2Fapi%2Fauth%2Fcallback%2Fgithub
      &code_challenge_method=S256
      &code_challenge=PoRscr6i1IYq_pQJI8XIAEzg_ZG_5NXGaZuBx8t-gyo",
    "redirect":true}

  ⇒ redirect_uri 가 G-1 이 만든 캐치올 라우트를 가리킨다 (복선 회수 지점)
  ⇒ state · PKCE · scope 가 전부 눈에 보인다

그 주소로 실제로 가보면:
  GitHub → HTTP/2 302
  location: https://github.com/login?client_id=demo-client-id&return_to=%2Flogin%2Foauth%2Fauthorize...
  ⇒ 우리 몫은 주소를 만드는 데까지. 그 다음은 GitHub 의 화면이다.
  ⇒ 끝까지 가려면 진짜 앱 등록이 필요하다 — 강의는 여기서 정직하게 멈춘다.


[6] 🚨 백엔드 화해의 실물 — 이름만 대면 그 사람이 된다
----------------------------------------------------------------------
api-stub 의 resolveActor (server.mjs:153-163):
  토큰이 없으면 X-Actor 헤더를 보고, findUser(actor) 가 있으면 통과.

우리 서버를 거치지 않고 스텁에 직접:
  POST /api/users/minji/follow  -H "X-Actor: jaehoon"  → 200
  POST /api/users/jaehoon/follow -H "X-Actor: minji"   → 200
  POST /api/users/minji/follow  -H "X-Actor: nobody"   → 401
  POST /api/users/minji/follow  (헤더 없음)             → 401

  ⇒ 존재하는 이름이기만 하면 누구든 그 사람이 된다.
  ⇒ G-1 Step 1 의 `me` 쿠키 위조와 똑같은 구조가 백엔드 쪽에 그대로 남아 있다.
  ⇒ 앞문에 서명을 붙였는데 뒷문은 서명 없는 이름 한 줄.

액션이 보내는 것 (app/actions/like.ts:28 · follow.ts:29):
  headers: { 'X-Actor': me }     ← me 는 currentUser() 가 준 진짜 신원이지만,
                                    스텁 입장에선 그것을 확인할 방법이 없다.

백엔드에 이미 있는 것: POST /api/auth/login  {username} → accessToken + refreshToken
  (비밀번호를 안 본다 — 스텁이라서. 토큰은 3회 사용 후 만료 = C-5 의 401 갱신 재료)
