[2] Step 3 채증 — prefetch 는 두 번에 나눠서 온다
----------------------------------------------------------------
/ 에 가만히 있는 동안(누르기 전) 나간 요청 4 건:

  /?_rsc=5CB68i4pnAekjehf              enc   200 B   tr   500 B
  /explore?_rsc=5CB68i4pnAekjehf       enc   212 B   tr   512 B
  /?_rsc=8nTjltbQWvg6NcbE              enc 1,693 B   tr 1,993 B
  /explore?_rsc=y5uIUfDQA6olE3D1       enc 1,786 B   tr 2,086 B
                                       ────────────
                                  합계 enc 3,891 B

앞의 두 건은 같은 토큰(5CB68i4pnAekjehf)이고 크기가 작다. 뒤의 두 건이
본체다. 화면에 뜬 직후에는 0 건이고 잠시 뒤에 나간다 — 페이지 로드 직후
바로 재면 "prefetch 가 없다" 는 잘못된 결론이 나온다. 3 초 기다렸다 쟀다.

⚠️ 그래서 "<Link> 는 요청이 0 건" 은 거짓이다. 정확히는 **누를 때 0 건**이고
요청은 시간축에서 앞으로 옮겨간 것이다. 총량도 138,128 → 3,891 B 로 줄었다.

[3] Step 2·4 채증 — 껍데기가 안 다시 그려지는 것을 세 가지로 확인
----------------------------------------------------------------
측정 시점: 최종 빌드(6cce107). / → /explore 를 <Link> 로 이동.

  콘솔에서 심은 window.__probe        '살아있음'  (JS 가 다시 시작 안 됐다)
  header 에 심은 data-probe-mark      'MARKED'   (그 DOM 이 새로 안 만들어졌다)
  검색칸에 쓰던 값                     '쓰던 값'   (클라이언트 상태가 안 날아갔다)
  aria-current                        홈 → 탐색으로 옮겨감

세 번째가 D-1 마무리가 약속한 바로 그것이다("스크롤 위치나 입력하던 값도
안 날아갑니다"). <a> 로 같은 이동을 하면 셋 다 초기화된다.

[4] Step 4 채증 — typedRoutes 는 켤 수 있고, 경계가 분명하다
----------------------------------------------------------------
next.config.ts 에 typedRoutes: true (Next 16 에서 정식 옵션.
experimental.typedRoutes 는 deprecated — config-shared.d.ts:830 실측).

켠 뒤 <Link href> 에 일부러 틀린 주소를 넣어봤다:

  href="/expolre"        → 통과한다 (!)
  href="/explore/foo"    → TS2820  Did you mean '"/explore"'?
  href="/settings/alarm" → TS2322

첫 줄이 통과하는 이유는 타입이 부실해서가 아니다. 생성된 타입을 보면

  type DynamicRoutes<T> = `/${SafeSlug<T>}`   // app/[username]/page.tsx

라서 **한 칸짜리 주소는 전부 진짜로 있는 주소**다. /expolre 는 expolre 라는
사람의 프로필이다. D-1 과제 3 이 런타임에서 발견한 것(Page.tsx 로 바꾸면
/explore 가 @explore 프로필을 그린다)이 타입에서 똑같이 재현된 것이다.

router.push(`/${trimmed}`) 도 같은 이유로 통과한다.

[6] Step 7 채증 — retry 와 reset 은 다른 물건이다
----------------------------------------------------------------
Next 16.3.0 에서 retry 가 stable 이 됐고 reset 은 "특별한 이유가 있을 때만"
으로 격하됐다(16.2.0 에 unstable_retry 로 먼저 들어왔다). 설치본 실측:

  next/dist/client/components/error-boundary.d.ts
    export type ErrorInfo = { error: unknown; reset: () => void; retry: () => void }

  error-boundary.js
    this.reset = () => { this.setState({ error: null }); }
    this.retry = () => { startTransition(() => { this.context?.refresh(); this.reset(); }) }

reset 은 상태만 지우고, retry 는 서버에 다시 물어본 다음 지운다.

브라우저 실측 (팔로워 집계가 세 번에 한 번만 성공하게 해둔 상태):

  retry 로 만들었을 때
    처음 화면      기록 번호 1983395149
    1 번 누름      기록 번호 3314094339   ← 번호가 바뀌었다 = 다시 물어봤다
    2 번 누름      회복 (팔로워 959 + 게시물 3 장)

  reset 으로 바꿔서 다시
    처음 화면      기록 번호 1983395149
    1~5 번 누름    1983395149 · 1983395149 · 1983395149 · 1983395149 · 1983395149
    결과           다섯 번 눌러도 그대로. 영영 회복 안 된다.

★ 기록 번호(error.digest) 하나가 "서버에 다시 물어봤나" 를 그대로 보여준다.
  눈으로 갈리는 지점이 이것뿐이라 교보재로 쓴다.

[9] ⚠️⚠️ 측정 사고 — 탭이 뒤에 있으면 prefetch 가 조용히 0 이 된다
----------------------------------------------------------------
Step 1 에서 prefetch 4 건을 재두고, 나중에 최종 상태에서 다시 쟀더니 0 건이
나왔다. 앱이 바뀌어서 그런 줄 알고 typedRoutes · error.tsx · not-found.tsx ·
머리말 클라이언트 컴포넌트화를 하나씩 되돌리며 4 번 이분 탐색했는데 전부 0 이었다.

원인은 앱이 아니었다:

  document.visibilityState  →  'hidden'
  document.hasFocus()       →  false

<Link> 의 prefetch 는 IntersectionObserver 로 "화면에 보이나" 를 판정한다.
탭이 뒤에 있으면 아무것도 안 보이므로 관찰자가 안 돈다. 그래서 0 이다.

스크린샷을 한 번 찍어 탭을 앞으로 꺼낸 뒤 다시 재니 곧바로 4 건이 돌아왔다.
→ prefetch 를 잴 때는 탭을 앞에 두고 재야 한다. 학생에게도 같은 조건이 필요하다.

교훈: 되돌려도 안 바뀌면 앱이 아니라 재는 환경을 의심한다.
