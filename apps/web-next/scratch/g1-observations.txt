■ 1. Step 1 — D-8 문지기가 무엇을 보나 (dev 서버)
  GET /jaehoon
    (쿠키 없음)   → 307      ← 막힌다
    me=jaehoon    → 200
    me=minji      → 200
    me=nobody     → 200      ← 없는 사람인데 통과
    me=           → 200      ← 빈 값도 통과 (proxy 는 === undefined 만 본다)
    me=x          → 200

  머리말 span(text-black/60) 이 그대로 믿는다:
    me=jaehoon  → @jaehoon
    me=minji    → @minji
    me=nobody   → @nobody    ← 앱이 쿠키를 그대로 이름으로 쓴다
    (쿠키 없음)  → "재훈으로 보기" / "민지로 보기" 버튼

  ⚠️ 측정 함정 1 — 처음에 grep '@[가-힣A-Za-z0-9_]*' 로 잡았더니
     Next 내부 문자열 "@boundary" 가 먼저 걸려 셋 다 같은 값이 나왔다.
     'text-black/60">@' 로 span 을 특정해야 참값.
  ⚠️ 측정 함정 2 — 한글 쿠키(me=아무나)는 curl 의 Cookie 헤더에서 깨진다
     (@ìë¬´ë). 앱 문제 아님. 교안은 ASCII 이름으로 재현시킨다.

■ 2. Step 1 — 위조한 신원으로 「행동」까지 되나
  위조 접속(me=nobody)으로 /minji 를 열면 팔로우 폼이 통째로 온다:
    $ACTION_REF_2  (값 없음)
    $ACTION_2:0    {"id":"6000c060bee...","bound":"$@1"}
    $ACTION_2:1    ["minji",{"following":null,"message":null}]
    $ACTION_KEY    kd2eec45c3fb1810fecc2c3a2d62171ed
  그 폼을 그대로 POST 하면 액션이 실제로 돈다 →
    [api-stub] POST /api/users/minji/follow      (로그에 찍힘)

  ⚠️ curl 로는 응답 본문을 못 받는다(스트리밍 화면 · 3분 타임아웃).
     D-8 canon 과 동일. 판정은 반드시 부작용(스텁 로그·집계값)으로.
  ⚠️ 처음 POST 는 $ACTION_REF_2 를 빠뜨려(value 속성이 없어 정규식이
     못 잡음) 액션이 안 돌았다. 4개를 다 실어야 한다.

■ 3. api-stub 의 방어선 — 이것은 인증이 아니다
  POST /api/users/minji/follow
    X-Actor: nobody    → 401 "로그인이 필요합니다"
    X-Actor: seungwoo  → 401   ← 게시물은 있지만 로그인 계정이 아니다
    X-Actor: jaehoon   → 200, followerCount 8500 → 8501
    (다시 부르면 토글 → 8500 복원)

  ★ 로그인 계정(USERS)은 jaehoon·minji 둘뿐이고,
    프로필 주인(게시물 작성자)은 10명이다 —
    dahye eunbi hyunwoo jaehoon jiwon junho minji seungwoo sora taeyang
  ★ 즉 스텁은 "그 이름이 계정 목록에 있나" 만 본다. 비밀번호도 서명도
    안 본다. 실존 계정 이름으로 위조하면 그대로 통과한다.

  라우트 표에 ƒ /api/auth/[...all] 추가, 나머지 라우트 기호 무변경
    ◐ / · ◐ /_not-found · ◐ /[username] · ƒ /api/auth/[...all]
    · ƒ /api/profiles/revalidate · ◐ /explore

  ⚠️ memoryAdapter(db) 에 빈 객체 {} 를 주면 런타임 500:
     [MemoryAdapter] Model user not found in the DB []
     → { user: [], session: [], account: [], verification: [] } 로 선언해야 한다.

■ 6. 가입·로그인 실측 (시크릿을 준 뒤)
  POST /api/auth/sign-up/email
    {"email":"jaehoon@example.com","password":"hunter22!","name":"재훈",
     "username":"jaehoon"}
    → 200 {"token":"...","user":{...,"username":"jaehoon",
            "displayUsername":"jaehoon","id":"VNazlnhPkYGCUs184wjty88U3vkgElg2"}}
  POST /api/auth/sign-in/username
    {"username":"jaehoon","password":"hunter22!"}  → 200
    {"username":"jaehoon","password":"wrong"}      → 401
      {"message":"Invalid username or password","code":"INVALID_USERNAME_OR_PASSWORD"}
  짧은 아이디는 플러그인이 막는다: username "aa" → {"code":"USERNAME_TOO_SHORT"}

■ 7. Step 4 척추 — 서명된 쿠키 vs 서명 없는 쿠키
  Set-Cookie: better-auth.session_token=<token>.<서명>;
              Max-Age=604800; Path=/; HttpOnly; SameSite=Lax
    예: RUlYj5NJEYxIWIuEVU3LlI2pV1uzhQvF.bAGOTlwmoKQn1M2T6P3wg0b6IMq89nkx4uJUpm19v9E%3D

  GET /api/auth/get-session 에 쿠키를 실어 보내면
    진짜 (대조군)          → 세션 + 사용자 반환
    쓰레기 값              → null
    토큰 진짜 + 서명만 위조  → null
    서명 진짜 + 토큰만 바꿈  → null

  ⚠️⚠️ 측정 함정 3 (가장 위험했다) — 처음엔 대조군까지 null 이 나와서
     "전부 거절된다" 로 결론 낼 뻔했다. 원인은 curl 이 HttpOnly 쿠키를
     쿠키 항아리에 "#HttpOnly_" 접두사로 저장하는데 grep -v '^#' 로
     걸러버린 것. 대조군이 통과하는지부터 확인해야 나머지가 의미를 갖는다.
     추출은 awk '/better-auth\.session_token/{print $NF}' 로.
