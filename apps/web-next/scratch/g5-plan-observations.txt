4절. matcher 를 넓히면 — 무한 리다이렉트는 안 났다. 대신 다른 것이 났다
-----------------------------------------------------------------------
matcher: ['/((?!api|_next|favicon.ico).*)']  +  PUBLIC_PATHS 에 '/', '/explore' 추가

  로그아웃 상태: /  200 · /explore 200 · /signup 200 · /jaehoon 307 · /zzzzz 307
  => D-8 채증의 「'/(.*)'로 넓히면 로그인이 무한 리다이렉트」는 PUBLIC_PATHS 로 풀린다.

⚠⚠ 그런데 목록에 없는 새 주소는 D-7 의 404 회복이 삼킨다.
   탐침 페이지 /g5probe 를 만들었더니 로그인 상태에서 404.
   문지기가 「g5probe 라는 사람 있나」를 묻고(GET /api/users/g5probe → 404)
   그대로 _not-found 로 rewrite 한 것. G-2 의 /signup 함정이 그대로 재현된다.
   => matcher 를 넓히는 순간 "새 주소를 만들 때마다 PUBLIC_PATHS 를 챙겨야 한다"
      는 부채가 생긴다. 교안이 이 대가를 정직하게 말해야 한다.

6절. 🚨🚨🚨 프로덕션에서 뒤집혔다 — 공식 예제 그대로 하면 앱의 JS 가 0개 실린다
--------------------------------------------------------------------------------
같은 빌드에서 CSP 만 토글해 A/B(측정 방법 동일 · 자원 타임라인의 decodedBodySize>0):

  CSP 없음                                   바이트 받은 JS 청크  9
  nonce + 'self' + 'strict-dynamic' (공식)   바이트 받은 JS 청크  0   ← CSS 1개만
  nonce + 'self' (strict-dynamic 제거)       바이트 받은 JS 청크  8

프로덕션 홈의 nonce 분포: 외부 1/10 · 인라인 31/32
nonce 를 못 받은 10개의 정체:
  - 외부 9개 = turbopack-*.js 포함 프레임워크 런타임 청크 전부(정적 껍데기에 박혀 있다)
  - 인라인 1개 = <Suspense> 자리의 $RT 성능 측정(D-5 가 넣은 자리)

'strict-dynamic' 은 script-src 의 호스트 표현('self')을 무효화한다.
그래서 정적 껍데기에 박힌 nonce 없는 <script src> 가 전부 거절된다.

⚠ 공식 문서가 이미 말하고 있었다 (같은 파일 397행):
  "Partial Prerendering (PPR) is incompatible with nonce-based CSP
   since static shell scripts won't have access to the nonce"
  그리고 181행: 정적 페이지는 빌드 때 만들어져 nonce 를 넣을 수 없다.
  우리는 D-5 에서 cacheComponents: true 를 켰다 = 전 라우트가 ◐(PPR).

=> G-4 채증 7·8절의 결론 「cacheComponents 와 충돌 없음 / 막히는 것은 성능 측정
   스크립트 하나뿐이고 화면과 무관하다」는 틀렸다. 근거가 두 가지로 좁았다:
     (a) 빌드 종료 코드로 판정했다 — 빌드는 실제로 exit 0 이고 라우트 표도 무변경이다
     (b) 인라인만 셌다 — 외부 1/10 을 적어두고도 그 뜻을 안 따라갔다
   빌드·라우트 표·상태 코드·화면(서버 HTML)이 전부 정상이라 아무도 안 알려준다.


6-2절. 원인을 갈랐다 — standalone 이 아니라 PPR 이다
----------------------------------------------------
검색으로 후보 원인이 둘 나왔다. 둘 다 열려 있는 upstream 이슈다.
  (a) PPR/cacheComponents 와 nonce 의 불화 — 공식 문서 397행 + issue #89754
      "Nonce-based CSP with inline <head> scripts is incompatible with cacheComponents"
      (2026-02-10 접수 · 열림 · Next 팀이 linear: next 라벨로 확인)
  (b) Turbopack + output:'standalone' 에서 nonce 가 안 붙는 버그 — issue #96063
      (16.2.10·16.2.11 재현 · 열림 · "the only way to keep an App Router app working
       is to keep 'unsafe-inline'")
  우리 앱은 Turbopack(16 기본) + output:'standalone' 이라 (b) 에 정확히 해당한다.

[갈랐다] 같은 빌드를 next start(비-standalone)로 띄워 재측정:
  standalone   외부 1/10 · 인라인 31/32
  next start   외부 1/10 · 인라인 31/32   ← 완전히 같다
=> (b) 는 우리 증상의 원인이 아니다. standalone 을 빼도 그대로다.

[확인] (a) 를 직접 끄려 했으나 끌 수 없다:
  cacheComponents: false 로 빌드 → exit 1.
  lib/api.ts 의 cacheLife/cacheTag 가 이 스위치를 전제로 한다(D-6 이 넣은 코드).
  => 「PPR 을 끄고 공식 예제를 쓴다」는 설정 한 줄이 아니라 D-6 을 걷어내는 일이다.

[확인] 완전 동적 라우트로 도망갈 수도 없다:
  문서는 "your page must be dynamically rendered" 라고 처방하는데,
  cacheComponents: true 에서는 페이지 라우트가 전부 ◐ 다(라우트 표 실측).
  ƒ 는 /api/* 두 개뿐이고 그것은 화면이 아니다.
  /explore 에 connection() 만 넣으면 프리렌더 단계에서 exit 1,
  <Suspense> 로 감싸도 D-5 canon 대로 ○→◐ 일 뿐 껍데기는 그대로 생긴다.

=> 원인은 (a) 로 확정. 그리고 문서의 처방은 우리 앱에서 도달 불가능하다.
   해법은 strict-dynamic 을 빼서 'self' 가 살아나게 하는 것이다(6절 표의 셋째 줄).
   ⚠ 대가: 'self' 는 같은 출처 스크립트를 전부 허용한다. 인라인 주입(G-4 페이로드)은
     여전히 막지만, 우리 출처에 파일을 올릴 수 있게 되면 그것은 막지 못한다.
     교안이 이 거래를 정직하게 말해야 한다.

⚠ 문서의 또 다른 대안 SRI(experimental.sri)도 우리에겐 안 닿는다 —
  webpack 전용이고 Turbopack(16 기본)에서 동작하지 않는다.


7절. ⚠️⚠️ 측정 함정 — 확장 프로그램의 격리 세계는 CSP 를 안 받는다
-------------------------------------------------------------------
CSP 강제 여부를 확인하려고 페이지에 script 요소를 만들어 붙였더니:
  nonce 없는 인라인 → 실행됨(true) · securitypolicyviolation 0건
=> 「CSP 가 안 걸려 있다」는 정반대 결론이 나온다.

원인: 도구가 주입한 코드는 확장 프로그램 격리 세계에서 돌아 페이지 CSP 를 안 받는다.

바로잡은 방법: 서버가 그린 HTML 안에 nonce 없는 인라인을 넣고(탐침 페이지에서
dangerouslySetInnerHTML 로 <script> 를 직접 그림 — Next 는 여기엔 nonce 를 안 붙인다)
그 부작용을 DOM 속성으로 읽었다(DOM 읽기는 숨은 탭에서도 유효).
  결과: data-inline-ran = null  →  차단됐다. CSP 는 실제로 강제되고 있다.

=> 「재는 방법이 답을 바꾼다」의 세 번째 종류. 주입으로는 CSP 를 못 잰다.


8절. CSRF — G-4 채증 13절 그대로 재현됐다
------------------------------------------
[서버 액션 · /minji 팔로우 · -F(multipart) 로 제출]
  우리 Origin              curl 000(스트리밍)  스텁 도달 2건 → 실행됨
  남의 Origin              curl 500            스텁 도달 0건 → 막힘
  Origin 없음              curl 000            스텁 도달 1건 → 통과

  서버 로그:
    `x-forwarded-host` header with value `localhost:3000` does not match `origin`
    header with value `evil.example.com` ... Aborting the action.
    ⚠ Missing `origin` header from a forwarded Server Actions request.   ← 없으면 경고만

[Route Handler · D-7 이 만든 /api/profiles/revalidate?username=jaehoon]
  우리 Origin + 쿠키          200
  남의 Origin + 쿠키          200
  Origin 없음 + 쿠키          200
  남의 Origin + 쿠키조차 없음  200   {"success":true,"data":{"username":"jaehoon"},...}

⚠ 내 첫 측정이 전부 400 이었다 — JSON 본문으로 보냈는데 이 라우트는 searchParams 를
  읽는다(route.ts:7). 계약을 안 읽고 짐작해서 「막혀 있다」로 읽을 뻔했다.
